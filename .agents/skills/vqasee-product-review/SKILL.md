# VQASee 产品审查：乔布斯

## 使命

把 VQASee 做成行人、骑行者、驾驶者、低视力用户和注意力可能分散的人都愿意使用的 iPhone 视觉风险辅助产品，而不是技术 demo。它提醒风险、边界和不确定性，但不替代用户观察或驾驶责任。

## 判断原则

1. 用户安全高于功能完整。
2. 少一步就是好一步。
3. 默认体验必须好，高级设置只能作为逃生门。
4. 用户不关心模型名、网络细节、token、队列；用户关心“我现在该怎么办”。
5. VQASee 不是聊天机器人，也不是自动驾驶系统；它首先是视觉风险辅助和环境提醒工具。
6. 不承诺“可以走/可以开”，只提示风险、边界、可疑轨迹和不确定性。

## 审查流程

### 1. 定义用户场景

回答：

- 谁在用？
- 在哪里用？
- 是走路、骑行、驾驶、过马路、找东西、读文字、看环境，还是问一个具体问题？
- 用户此刻有没有手操作手机的能力？是否处在注意力分散或交通风险场景？
- 如果失败，最坏后果是什么？

### 2. 定义核心价值

用一句话写：

```text
这个功能帮助用户在 <场景> 中更好地 <完成任务>。
```

如果写不出来，先不要做。

### 3. 砍掉复杂度

主动问：

- 有没有按钮可以删？
- 有没有设置可以隐藏？
- 有没有文案可以缩短？
- 有没有模式可以自动判断？
- 有没有技术概念暴露给了用户？

### 4. 确定成功指标

每个产品改动至少有一个指标：

- 首次成功连接时间；
- 用户从打开 app 到听到第一句有效反馈的时间；
- walking / riding / driving-risk 场景有效提醒率；
- 误播报率；
- 用户是否需要进入高级设置；
- 读文字成功率；
- 断线恢复成功率。

### 5. 输出产品决定

使用：

```text
结论：做 / 不做 / 延后 / 先实验
理由：...
最小版本：...
不做什么：...
验收标准：...
```

## 发布标准

一个功能进入发布前，必须满足：

- 用户知道它什么时候在工作；
- 失败时用户知道发生了什么；
- 普通用户和低视力用户都不用读复杂说明；
- 不增加核心流程负担；
- 有基本测试或人工验收步骤。
