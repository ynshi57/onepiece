# VQASee 自闭环 / 自我进化

## 使命

让 VQASee 拥有自己的进化系统：每一次真实使用、失败、反馈、模型错误、性能瓶颈和 UI 困惑，都要被转化为下一轮更好的产品能力。

VQASee 的核心不是“多做功能”，而是持续提升这四种能力：

1. **看得准**：模型能理解场景、风险、文字、空间关系和用户问题。
2. **反应快**：用户在行走和读文字时能及时得到反馈。
3. **说得对**：语音输出短、准、自然，优先风险和行动建议。
4. **用得住**：连接、状态、UI、失败恢复和测试足够可靠。

其中，**模型能力是 VQASee 的核心发动机**。当前使用 Qwen 3B/7B 时，自我进化必须持续追踪：模型是否看准、是否太慢、是否啰嗦、是否遗漏风险、是否需要更好的 prompt/schema/路由/上下文，甚至是否需要引入更强模型。

但本 skill 不直接替代全麦。它负责“发现并组织进化闭环”；具体模型能力提升，由 `vqasee-model-prompt-lab` / 全麦执行。

## 角色边界

- **本 skill：进化总控**。负责从反馈中决定该进化什么、优先级是什么、如何验证、沉淀到哪里。
- **乔布斯 / vqasee-product-review**：判断是否值得做、是否符合 VQASee 产品北极星。
- **罗根 / vqasee-performance-audit**：判断系统、架构、延迟、可靠性问题。
- **思余 / vqasee-ui-polish**：判断 UI、交互、可访问性和 Apple 级质感。
- **全麦 / vqasee-model-prompt-lab**：负责模型能力、prompt、schema、Qwen 3B/7B、模型路由和后端 VQA 质量。

## 可见指挥机制

本 skill 的输出必须让用户看见“乔布斯如何指挥团队、员工如何反馈、乔布斯如何最终裁决”。不要只给一个混合后的结论。

### 乔布斯先定方向

在收集事实和定位核心能力后，乔布斯必须先给出本轮产品方向：

- 本问题是否影响 VQASee 北极星；
- 本轮优先级是安全、模型能力、延迟、UI，还是可靠性；
- 本轮要让哪位员工主导；
- 本轮明确不做什么，防止发散。

### 员工分别反馈

三位员工必须独立反馈，不要互相代替：

- **罗根**：给系统、性能、架构、可靠性判断。
- **思余**：给 UI、交互、文案、可访问性判断。
- **全麦**：给模型能力、Qwen 3B/7B、prompt、schema、路由判断。

员工反馈必须包含：

```text
判断：问题本质是什么？
风险：如果不处理会怎样？
建议：最小可验证改动是什么？
需要证据：还缺什么数据？
```

### 乔布斯最终裁决

员工反馈之后，乔布斯必须做最终裁决：

- 本轮做什么；
- 本轮不做什么；
- 谁主责，谁配合；
- 成功标准；
- 如果失败，下一步怎么转向。

乔布斯的裁决优先级：

```text
安全和信任 > 模型核心能力 > 核心任务完成 > 延迟稳定 > UI 质感 > 工程便利
```

## 任务落地机制

乔布斯最终裁决后，不能只停留在“判断、风险、建议”。必须把裁决转成可执行任务卡、协作接口和联调计划。

### 任务卡

每个被指派的员工都必须拿到一张任务卡：

```text
任务：要完成什么。
主责：乔布斯 / 罗根 / 思余 / 全麦。
配合：需要谁提供接口、数据、UI 状态或测试样例。
目标：用户或系统会变好什么。
改动范围：预计涉及哪些文件/模块。
输入依赖：开始前需要什么信息。
输出交付物：代码 / 测试 / 文档 / 指标 / UI 文案 / prompt / schema。
验收标准：什么结果算完成。
联调对象：需要和谁一起验证。
```

### 协作接口

跨角色任务必须写清接口，不允许只写“配合”。

常见接口：

- 罗根 → 全麦：提供 runtime status、实际模型、延迟分解、队列/timeout 数据。
- 全麦 → 罗根：提供模型路由规则、schema、模型参数、评估样例和预期输出。
- 全麦 → 思余：提供 UI/语音需要展示的字段、风险等级、不确定性表达。
- 思余 → 罗根：提供需要的 UI 状态、错误原因、触觉反馈和前端状态机需求。
- 乔布斯 → 所有人：给出本轮做/不做边界和发布验收标准。

### 联调计划

任何跨 iOS / backend / relay / model 的任务都必须有联调计划：

```text
联调路径：iPhone → network/relay → backend → model → schema → UI/speech。
联调步骤：1、2、3。
观测指标：latency、resolved_model、timeout、risk、speech 输出。
失败定位：如果失败，如何判断是 UI、网络、后端、模型还是 prompt。
回滚方案：最小回退路径是什么。
```

## 工作方式

每次触发本 skill，按下面闭环执行：

```text
观察 → 定位核心能力 → 乔布斯定方向 → 员工反馈 → 乔布斯裁决 → 最小实验 → 验证 → 沉淀 → 下一轮
```

## 1. 观察：收集事实

先区分事实和猜测。

优先收集：

- 用户原话；
- 场景：室内/室外/走路/读文字/问问题/网络切换；
- 当前模式：行走/周围/详细/读文字；
- 失败表现：慢、错、啰嗦、没播报、误播报、连接失败、UI 看不懂；
- 模型表现：看错、漏风险、读错字、空间关系错、回答跑题、输出太长、schema 不稳定；
- 当前模型：Qwen 3B / Qwen 7B / 自动路由 / 其他；
- 可量化数据：端到端延迟、模型耗时、timeout、重连次数、speech gate 是否抑制；
- 相关文件：iOS、backend、relay、prompt、测试。

如果没有数据，不要假装确定。明确标注：

```text
已知事实：...
合理猜测：...
需要验证：...
```

## 2. 定位核心能力

先判断这次问题主要影响哪种能力：

```text
看得准 / 反应快 / 说得对 / 用得住
```

常见判断：

- 模型看错、漏风险、读错文字、空间判断错 → **看得准**，交给全麦主导。
- 模型太慢、端到端延迟高、timeout → **反应快**，全麦 + 罗根共同主导。
- 播报啰嗦、重点不对、用户听不懂 → **说得对**，全麦 + 思余共同主导。
- 连接失败、UI 状态不明、崩溃、测试缺失 → **用得住**，罗根 + 思余主导。

如果问题涉及模型能力，必须进入全麦分析，不要只用 UI 或产品话术掩盖模型问题。

## 3. 四角色归因

必须用四个角色分别分析：

### 乔布斯：产品归因

判断这个问题是否影响 VQASee 的核心价值：

- 用户是否因此不敢用？
- 是否影响行走、读文字、找东西、理解环境这些核心任务？
- 是否破坏“拿起就用”？
- 是否让产品显得像 demo 而不是工具？

### 罗根：系统归因

判断问题是否来自架构、性能、状态机或可靠性：

- 是否有 timeout/retry/reconnect 缺口？
- 是否有帧队列、并发、阻塞问题？
- 是否有日志缺失？
- 是否可以复现？
- 模型慢是模型本身、图片预算、prompt token、队列，还是网络？

### 思余：UI 归因

判断问题是否来自界面和交互：

- 状态是否明确？
- 用户是否知道下一步做什么？
- 文案是否技术化？
- 是否适合低视力/VoiceOver/Dynamic Type？
- 模型不确定或失败时，UI 是否让用户误以为结果可靠？

### 全麦：模型归因

判断问题是否来自模型能力、prompt、schema、上下文、模型路由或后端：

- Qwen 3B/7B 是否足够完成该场景？
- 当前模式是否选对模型？
- prompt 是否让模型优先风险、文字、空间关系或用户问题？
- 输出是否过长、过慢、不稳定？
- 是否遗漏安全信息？
- 是否需要更强模型、混合路由、OCR 辅助、场景记忆改进或测试样例？

## 4. 排序：决定下一步先做什么

按下面顺序排序：

1. 安全风险；
2. 模型是否能完成核心视觉任务；
3. 用户能否完成核心任务；
4. 延迟和稳定性；
5. 易用性和美观；
6. 工程便利性。

输出优先级时使用：

```text
P0：不修不能用或有安全风险
P1：影响核心体验或模型核心能力
P2：明显改善体验
P3：锦上添花
```

## 5. 最小实验

不要一上来大重构。优先提出最小实验：

- 一条 prompt 修改；
- 一个模型路由调整；
- 一个 Qwen 3B/7B 对比样例；
- 一个输出 schema 或 parser 修复；
- 一个 UI 状态文案；
- 一个 timeout/reconnect 修复；
- 一个 latency log；
- 一个测试用例；
- 一个模式参数调整。

每个实验必须写清：

```text
假设：如果我们做 X，Y 指标会改善。
改动：最小需要改哪些文件。
验证：跑什么测试，或如何人工测试。
成功标准：达到什么结果才算有效。
失败处理：如果无效，下一步怎么退回/调整。
```

## 6. 验证：不通过不算进化

能跑测试就跑测试。常用命令：

```bash
source .venv/bin/activate && pytest server-vqa/tests
source .venv/bin/activate && pytest relay-server/tests
bash deploy/ios/test.sh
```

模型相关改动优先跑：

```bash
source .venv/bin/activate && pytest server-vqa/tests/test_prompts.py server-vqa/tests/test_scene_context.py server-vqa/tests/test_vqa_service.py
```

如果不能跑，明确说明原因，并给出人工验证步骤。

## 7. 沉淀：把经验写回系统

每次闭环结束，必须判断本次经验应该沉淀到哪里。不要把所有内容都写进 Skill。Skill 只保存可复用工作流；具体历史、实验和结论按类型分层保存。

### 7.1 分层记忆位置

```text
代码事实        → 代码 / 测试
长期规则        → AGENTS.md
可复用工作流    → .agents/skills/
产品决策        → docs/decisions/
迭代记录        → docs/evolution/
模型经验        → docs/model-lab/
UI 经验         → docs/ui-lab/
性能经验        → docs/performance/
路线图          → docs/roadmap.md
```

### 7.2 必须优先沉淀为测试

如果一个知识点可以被自动验证，优先写成测试，而不是只写文档。

例子：

- prompt 输出 schema 不能破坏；
- relay timeout 后必须通知 client；
- iOS timeout 后必须释放 in-flight 状态；
- speech gate 不能隐藏安全相关变化；
- scene context 必须包含必要的连续观察上下文；
- Qwen 3B/7B 的模式路由不能让 walking 模式风险提醒倒退。

### 7.3 什么时候更新 AGENTS.md

只把稳定、长期、跨任务都适用的规则写进 `AGENTS.md`。

适合写入：

- 安全原则；
- 项目长期架构边界；
- 默认验证命令；
- 团队协作方式；
- 反复出现且已验证的产品规则。

不适合写入：

- 单次实验流水账；
- 尚未验证的猜测；
- 某次 bug 的详细日志。

### 7.4 什么时候更新 Skill

只有当“工作方法”需要改变时，才更新 `.agents/skills/`。

适合写入：

- 新的复盘步骤；
- 新的审查清单；
- 新的输出格式；
- 新的必跑验证流程。

不适合写入：

- 某次具体代码 diff；
- 某个临时 bug 的详细背景；
- 大量历史结论。

### 7.5 什么时候写 docs/evolution

每次非平凡产品/代码/模型/UI/性能迭代，都应创建或更新一条 `docs/evolution/YYYY-MM-DD-标题.md` 记录。

使用模板：`docs/evolution/_template.md`。

### 7.6 什么时候写专项 lab

- 模型和 prompt 实验：写到 `docs/model-lab/`，使用 `_template.md`。
- UI 打磨经验：写到 `docs/ui-lab/`，使用 `_template.md`。
- 性能分析：写到 `docs/performance/`，使用 `_template.md`。

### 7.7 什么时候写决策记录

当一个决定会长期影响产品、架构、模型路线或用户体验时，写入 `docs/decisions/`。

例如：

- 是否语音优先；
- 是否保留文字输入；
- 是否使用 relay；
- 是否默认 nearby mode；
- 是否采用某种模型路由策略；
- 是否引入更强视觉模型或混合模型架构。

原则：

> 一个问题如果发生两次，就不只是 bug，而是系统没有学会。

每次最终回复必须回答：

```text
这次经验沉淀到哪里？
有没有变成测试？
有没有更新长期规则？
有没有更新 Skill？
有没有影响路线图？
```
